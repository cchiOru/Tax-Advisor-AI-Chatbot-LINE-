## ส่วนที่ 5: สิ่งที่ทำได้เกินกว่าที่นำเสนอไว้

รายการเหล่านี้ไม่ได้อยู่ในแผนเดิม แต่เพิ่มคุณค่าเชิงวิชาการให้งาน

1. **เครื่องคำนวณภาษีแบบกำหนดผลได้แน่นอน พร้อมชุดทดสอบ 32 กรณี**
   ย้ายการคำนวณออกจากแบบจำลองภาษามาไว้ในโค้ดที่เขียนตามประมวลรัษฎากร
   ทำให้ผลลัพธ์ตรวจสอบซ้ำได้ ต่างจากสไลด์ที่ให้แบบจำลองคำนวณเอง

2. **หน่วยความจำบทสนทนาแบบถาวร**
   ข้อมูลไม่หายเมื่อรีสตาร์ทระบบ ตรงตามขอบเขตข้อ 4 ที่ระบุว่าต้องเก็บไว้วิเคราะห์

3. **การบันทึกข้อมูลเชิงวิจัยอัตโนมัติ**
   เก็บเวลาตอบสนอง จำนวนรายการความรู้ที่ค้นเจอ และชื่อแบบจำลองที่ใช้
   พร้อม view สำเร็จรูปสำหรับคำนวณค่าเฉลี่ยและส่วนเบี่ยงเบนมาตรฐาน

4. **การทดลองเปรียบเทียบแบบจำลองภาษา 3 ตัว**
   ควบคุมตัวแปรครบถ้วน วัดอัตราการเรียกใช้เครื่องมือ ความถูกต้อง และเวลาตอบสนอง
   เป็นการทดลองที่ไม่มีในแผนเดิมและเพิ่มน้ำหนักให้บทที่ 4 อย่างมาก

5. **กระบวนการสร้างระบบที่ทำซ้ำได้**
   มีสคริปต์ประกอบ workflow อัตโนมัติ และไฟล์ migration ฐานข้อมูล
   ทำให้ผู้อื่นติดตั้งซ้ำแล้วได้ระบบเดียวกัน

## ส่วนที่ 6: ข้อผิดพลาดที่พบในสไลด์ ต้องแก้ก่อนใช้อ้างอิงต่อ

### สไลด์ที่ 15 — ตัวเลขการคำนวณภาษีไม่ถูกต้อง

สไลด์แสดงว่า:

```
รายได้      : 600,000
ค่าใช้จ่าย   : -150,000     ← ผิด
ลดหย่อน     : -60,000
สุทธิ        : 390,000      ← ผิด
ภาษีรวม     ≈ 16,500 บาท   ← ผิด
```

ค่าที่ถูกต้องตามประมวลรัษฎากร มาตรา 42 ทวิ กรณีเป็นเงินได้จากเงินเดือน 40(1):

```
รายได้      : 600,000
ค่าใช้จ่าย   : -100,000     (หัก 50% แต่เพดาน 100,000 บาท)
ลดหย่อน     : -60,000
สุทธิ        : 440,000
ภาษีรวม     = 21,500 บาท
```

**ต่างกัน 5,000 บาท** สาเหตุคือหักค่าใช้จ่ายเกินเพดานที่กฎหมายกำหนดไป 50,000 บาท

ตัวเลข 21,500 บาท ตรวจสอบได้จากเครื่องคำนวณของระบบ:
```powershell
node -e "const c=require('./n8n/tools/tax-calculator');console.log(c.calculateThaiPIT({income:{salary:600000}})['สรุป'])"
```

> **ข้อดีของการค้นพบนี้:** เป็นหลักฐานที่หนักแน่นมากว่าทำไมต้องแยกการคำนวณ
> ออกจากแบบจำลองภาษา สามารถนำไปเขียนในบทที่ 3 หรือใช้ตอบกรรมการได้โดยตรงว่า
> "ระบบเวอร์ชันแรกที่ให้แบบจำลองภาษาคำนวณเอง ให้ผลคลาดเคลื่อนจากกฎหมายจริง
> จึงเป็นเหตุผลที่ออกแบบให้เรียกใช้เครื่องมือคำนวณแทน"

## ส่วนที่ 8: ทางเลือกในการปิดช่องว่าง

มีสองทางที่เป็นไปได้ ควรปรึกษาอาจารย์ที่ปรึกษาก่อนตัดสินใจ

**ทางที่ 1: ทำให้ครบตามที่นำเสนอ**
พัฒนา Workflow ตัวที่ 2, Rich Menu และ Embeddings เพิ่ม
ข้อดีคือตรงกับที่นำเสนอไว้ทุกประการ ข้อเสียคือใช้เวลามากและอาจกระทบกำหนดส่งเล่ม

**ทางที่ 2: ปรับขอบเขตในเล่มให้ตรงกับสิ่งที่ทำจริง แล้วอธิบายเหตุผล**
ระบุในบทที่ 3 ว่าเปลี่ยนจาก Embeddings เป็น Full-Text Search เพราะเหตุใด
และย้าย Workflow ตัวที่ 2 ไปเป็นแนวทางพัฒนาต่อในบทสรุป
ข้อดีคือใช้เวลาน้อยและยังคงความซื่อตรงทางวิชาการ
ข้อเสียคือขอบเขตแคบกว่าที่นำเสนอ จึงต้องอธิบายเหตุผลให้หนักแน่น

> การปรับขอบเขตระหว่างทางเป็นเรื่องปกติในงานวิจัย ตราบใดที่ระบุไว้ชัดเจน
> พร้อมเหตุผลรองรับ สิ่งที่ยอมรับไม่ได้คือการเขียนว่าทำแล้วทั้งที่ยังไม่ได้ทำ
