# 08 — ความแม่นยำและการนำไปใช้จริง

เอกสารนี้ตอบคำถามเดียว: **"คุณภาษี" แม่นพอจะให้คนจริงใช้หรือยัง**

คำตอบตรงไปตรงมาคือ ตอนนี้ยัง **ไม่รู้** เพราะยังไม่เคยวัดความแม่นยำแบบครบวงจร
เอกสารนี้จึงเป็นทั้งวิธีวัด เกณฑ์ตัดสิน และมาตรการที่ต้องมีก่อนเปิดใช้

> ทำไมต้องซีเรียส: ถ้าบอทตอบตัวเลขผิด ผู้ใช้อาจยื่นภาษีผิดแล้วโดนเงินเพิ่มตาม
> ประมวลรัษฎากร มาตรา 27 (ร้อยละ 1.5 ต่อเดือน) กับค่าปรับตามมาตรา 35
> ความเสียหายตกอยู่กับผู้ใช้ ไม่ใช่ผู้พัฒนา นี่คือเหตุผลที่ต้องวัดก่อนเปิด

---

## ส่วนที่ 1 — ทำไมความแม่นยำของระบบนี้ไม่ได้ขึ้นกับแบบจำลองภาษาอย่างเดียว

คำตอบหนึ่งคำตอบต้องผ่าน 4 จุด แต่ละจุดพังได้คนละแบบ

| จุด | ทำหน้าที่ | พังแบบไหน | เราป้องกันยังไง |
|---|---|---|---|
| 1. จำแนกเจตนา (Build Context) | แยกว่าคำถามเป็นหมวดไหน | จัดหมวดผิด | กฎแบบมีลำดับ ทดสอบแล้ว 15/15 |
| 2. ค้นฐานข้อมูล (RAG) | ดึงมาตรากฎหมายที่เกี่ยวข้อง | ค้นไม่เจอ หรือเจอผิดเรื่อง | จับคู่คำสำคัญ 116 คู่ + ถ่วงน้ำหนัก title×5 category×3 content×1 |
| 3. คำนวณ (เครื่องมือ) | คิดเลขภาษี | คิดเลขผิด | โค้ดที่ทดสอบแล้ว 40 ข้อ ไม่ให้แบบจำลองคิดเอง |
| 4. เรียบเรียงคำตอบ (LLM) | เขียนเป็นภาษาคน | เดาตัวเลขเอง / ตอบข้อมูลดิบ | ด่านตรวจ + คำเตือนบังคับ ทดสอบแล้ว 20 ข้อ |

**จุดที่อันตรายที่สุดคือจุดที่ 4 ในกรณีที่แบบจำลองไม่ยอมเรียกเครื่องมือ**
เพราะเครื่องคำนวณจะแม่นแค่ไหนก็ไม่มีความหมาย ถ้าแบบจำลองเลือกจะเดาเลขเอง
ตัวเลขที่ได้จะดู "สมเหตุสมผล" แต่ไม่มีอะไรรับประกันเลย และผู้ใช้แยกไม่ออก

ด้วยเหตุนี้ ตัวชี้วัดสำคัญของงานนี้จึงมี **สองตัว** ไม่ใช่ตัวเดียว

- **ความแม่นยำโดยรวม** — ตอบถูกกี่เปอร์เซ็นต์
- **อัตราการเรียกเครื่องมือเมื่อจำเป็น** — คำถามที่มีตัวเลข ผ่านเครื่องคำนวณกี่เปอร์เซ็นต์

ตัวที่สองสำคัญกว่าที่คนมักคิด เพราะมันคือตัวที่บอกว่าความถูกต้อง
เกิดจาก "ระบบที่ตรวจสอบได้" หรือเกิดจาก "โชค"

### 2.2.1 เมื่อโควตาของแบบจำลองหมดกลางทาง

Gemini รุ่นใช้ฟรีมีโควตาจำกัดต่อวัน และคำถามหนึ่งข้อใช้การเรียก API อย่างน้อย 2 ครั้ง
(ครั้งแรกเรียกเครื่องมือคำนวณ ครั้งที่สองเรียบเรียงคำตอบ) โควตาจึงหมดได้ก่อนวัดครบ 32 ข้อ

เครื่องมือวัดจัดการเรื่องนี้ไว้แล้ว ด้วยหลักการสำคัญคือ
**"โควตาหมด" ไม่ใช่ "ตอบผิด"** จึงไม่ถูกนับรวมในความแม่นยำ

- ผลรายข้อถูกบันทึกลง `evaluation/results/.checkpoint-<แบบจำลอง>.json` ทันทีที่วัดเสร็จ
- เมื่อเจอโควตาหมดติดกัน 3 ข้อ ระบบจะหยุดเอง แทนที่จะเสียเวลารอไปเรื่อย ๆ
- รันคำสั่งเดิมซ้ำเมื่อโควตากลับมา ระบบจะข้ามข้อที่วัดแล้วและวัดต่อจากข้อที่ค้าง
- ถ้าคำสั่งระบบ เครื่องมือ หรือคำสำคัญถูกแก้ไข ผลเดิมจะถูกทิ้งอัตโนมัติ
  (เทียบด้วยลายนิ้วมือของการตั้งค่า) เพื่อไม่ให้ผลคนละเวอร์ชันปนกัน

**ทางเลือกเมื่อโควตาหมด** เรียงตามความเหมาะสม

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| รอโควตารีเซ็ตแล้วรันซ้ำ | ฟรี ผลต่อเนื่องกับของเดิม | ต้องรอข้ามวัน |
| `--model=typhoon` (รันในเครื่อง) | ไม่มีโควตา วัดครบ 32 ข้อรวดเดียว | ช้ากว่า และเป็นคนละแบบจำลองกับที่ตั้งใจใช้จริง |
| `--model=openai` (gpt-4o-mini) | เร็ว เสถียร วัดครบในครั้งเดียว | มีค่าใช้จ่าย (32 ข้อ ประมาณไม่ถึง 2 บาท) |

ในเชิงวิจัย การวัดทั้งสามแบบแล้วรายงานเปรียบเทียบมีคุณค่ากว่าการวัดแบบเดียว
เพราะแสดงให้เห็นว่าความแม่นยำของระบบขึ้นกับแบบจำลองมากน้อยเพียงใด

ผลรายข้อบันทึกเป็น CSV ไว้ที่ `evaluation/results/` เปิดด้วย Excel ได้เลย
ใช้เป็นตารางในบทที่ 4 ของปริญญานิพนธ์ได้โดยตรง

### 2.3 ก่อนวัด ต้องนำเข้าเวิร์กโฟลว์ใหม่ก่อน

### 2.2.2 ก่อนเชื่อผลของ Typhoon ต้องตรวจหน้าต่างบริบทก่อน

ข้อมูลนำเข้าของระบบนี้ยาวประมาณ **9,400 ตัวอักษร (~6,300 โทเคน)**
ขณะที่ Ollama ตั้งหน้าต่างบริบทเริ่มต้นไว้เพียง **4,096 โทเคน**
และเมื่อเกิน Ollama จะ **ตัดข้อมูลส่วนหน้าทิ้งโดยไม่แจ้งเตือน**

ส่วนหน้าที่ถูกตัดคือคำสั่งระบบ ตัวบทกฎหมายที่ค้นมา และนิยามเครื่องมือคำนวณ
กล่าวคือแบบจำลองไม่รู้ว่าตัวเองเป็นใคร ไม่เห็นกฎหมาย และไม่รู้ว่ามีเครื่องคำนวณ

**ผลที่วัดได้ในสภาพนี้จึงไม่ใช่ความสามารถจริงของแบบจำลอง แต่เป็นผลของการตั้งค่าที่ผิด**
ต้องแก้ตามขั้นตอนใน `n8n/ollama/README.md` แล้ววัดซ้ำด้วย `--fresh` ก่อนนำผลไปรายงาน

เครื่องมือวัดจะเตือนอัตโนมัติเมื่อตรวจพบสภาพนี้

## ส่วนที่ 3 — เกณฑ์ตัดสิน

| ความแม่นยำ | อัตราเรียกเครื่องมือ | แปลว่า |
|---|---|---|
| ≥ 90% | ≥ 98% | ทดลองใช้กับผู้ใช้จริงได้ **โดยยังต้องมีคำเตือนทุกคำตอบ** |
| ≥ 80% | — | ใช้สาธิต/นำเสนอได้ แต่ยังไม่ควรเปิดให้คนทั่วไป |
| < 80% | — | ยังไม่พร้อม ต้องแก้ที่ต้นเหตุก่อน |

เกณฑ์เหล่านี้ตั้งจากลักษณะความเสี่ยงของงาน ไม่ใช่ตัวเลขมาตรฐานสากล
ให้ระบุที่มาของเกณฑ์ไว้ในปริญญานิพนธ์ด้วย เพื่อความโปร่งใสทางวิชาการ

### อ่านผลยังไงต่อ

- **ผิดกระจุกในหมวดเดียว** → ปัญหาอยู่ที่ฐานข้อมูลหรือคำสำคัญของหมวดนั้น เพิ่มข้อมูลใน `postgres/seed-tax-law-extra.sql`
- **ผิดกระจายทุกหมวด** → ปัญหาอยู่ที่คำสั่งระบบหรือความสามารถของแบบจำลอง ลองสลับแบบจำลอง
- **อัตราเรียกเครื่องมือต่ำ** → ปัญหาร้ายแรงที่สุด แก้ที่คำอธิบายเครื่องมือใน `build-workflow.py` ให้ชัดขึ้น หรือเปลี่ยนไปใช้แบบจำลองที่เรียกเครื่องมือได้ดีกว่า
- **ผิดเฉพาะข้อระดับยาก** → ยอมรับได้ในเชิงวิจัย แต่ต้องรายงานตรง ๆ ว่าระบบมีขีดจำกัดตรงไหน

## ส่วนที่ 4 — มาตรการที่ต้องมีก่อนเปิดใช้จริง

### 4.1 คำเตือนท้ายคำตอบ — ทำแล้ว

คำเตือนถูก **ต่อท้ายด้วยโค้ด** ในโหนด `Prepare LINE Reply` ไม่ได้ปล่อยให้แบบจำลองตัดสินใจ

```
— ข้อมูลนี้เป็นการประมาณการเบื้องต้นเพื่อการศึกษา
โปรดตรวจสอบกับกรมสรรพากร สายด่วน 1161 หรือ rd.go.th ก่อนยื่นจริง
```

เหตุผลเชิงออกแบบ: คำสั่งระบบสั่งให้แบบจำลองเตือนอยู่แล้ว แต่แบบจำลองอาจลืม
ซึ่งยอมรับไม่ได้เมื่อใช้งานจริง การบังคับด้วยโค้ดทำให้เป็น 100% แน่นอน
และการตัดความยาวกันที่ให้คำเตือนไว้ก่อน คำเตือนจึงไม่มีวันถูกตัดหาย

ตรวจสอบได้ด้วย `node --test tests/test-reply-guard.js` (20 ข้อ)

### 4.2 ด่านตรวจคำตอบผิดรูปแบบ — ทำแล้ว

แบบจำลองขนาดเล็กบางครั้งพิมพ์ข้อมูลนำเข้าของเครื่องมือออกมาเป็นคำตอบ
เช่น `{"taxDue":10000,"monthsLate":3}` ด่านนี้ดักไว้แล้วเปลี่ยนเป็นข้อความที่ผู้ใช้เข้าใจได้

### 4.3 สิ่งที่ยังต้องทำก่อนเปิดให้คนนอกใช้

| เรื่อง | ทำไมจำเป็น | สถานะ |
|---|---|---|
| ข้อความต้อนรับที่บอกขอบเขตและข้อจำกัด | ผู้ใช้ต้องรู้ตั้งแต่แรกว่านี่ไม่ใช่คำปรึกษาทางกฎหมาย | ยังไม่ทำ (ตั้งได้ที่ LINE OA Manager → Greeting message) |
| Rich Menu ที่มีปุ่ม "ติดต่อกรมสรรพากร 1161" | ทางออกเมื่อระบบตอบไม่ได้ | ยังไม่ทำ |
| แจ้งว่าเป็นระบบเพื่อการศึกษา/วิจัย | ความโปร่งใสและการขอความยินยอมเก็บข้อมูล | ยังไม่ทำ |
| นโยบายข้อมูลส่วนบุคคล (PDPA) | ระบบเก็บ LINE user ID, ชื่อ, รูป, ข้อความ ซึ่งเป็นข้อมูลส่วนบุคคล | ยังไม่ทำ |
| ตรวจว่าคำตอบไม่ได้อ้าง `revenue_code_sections` | ตารางนั้นเป็นตัวบทฉบับ พ.ศ. 2482 ตัวเลขล้าสมัย | ปลอดภัยอยู่ (RAG อ่านจาก `tax_law_knowledge` เท่านั้น) |
| ระบบพร้อมใช้ตลอดเวลา | ปัจจุบันรันผ่าน ngrok บนเครื่องส่วนตัว ปิดเครื่องคือบอทตาย | อยู่นอกขอบเขตที่ตกลงกันแล้ว |

### 4.4 ข้อควรระวังที่ต้องเขียนลงปริญญานิพนธ์

1. **ระบบครอบคลุมเฉพาะภาษีเงินได้บุคคลธรรมดา** ไม่รวมภาษีนิติบุคคล VAT ภาษีที่ดิน
2. **ฐานข้อมูลอ้างอิงกฎหมายปีภาษีที่ระบุไว้ในโค้ด** (`TAX_YEAR`) กฎหมายภาษีแก้ทุกปี ต้องมีแผนปรับปรุง
3. **ระบบไม่ทราบข้อเท็จจริงเฉพาะบุคคล** เช่น สถานะการหักภาษี ณ ที่จ่ายจริง จึงเป็นการประมาณการเสมอ
4. **ไม่ใช่การให้คำปรึกษาทางกฎหมาย** ตามความหมายทางวิชาชีพ

## ส่วนที่ 5 — ลำดับที่ควรทำต่อ

1. นำเข้าเวิร์กโฟลว์ใหม่เข้า n8n (ส่วนที่ 2.3)
2. รัน `node evaluation/run-accuracy-test.js --model=gemini` แล้วดูตัวเลข
3. ถ้าไม่ถึงเกณฑ์ → ดูตารางในส่วนที่ 3 ว่าควรแก้ตรงไหน แล้ววัดซ้ำ
4. ถ้าถึงเกณฑ์ → ตั้งข้อความต้อนรับ + Rich Menu (ส่วนที่ 4.3) แล้วเริ่มทดลองกับผู้ใช้กลุ่มเล็ก
5. เก็บข้อมูลการใช้งานจริงจากฐานข้อมูล (`v_response_time_stats`, `v_intent_stats`, `v_daily_usage`) ไปเขียนบทที่ 4
