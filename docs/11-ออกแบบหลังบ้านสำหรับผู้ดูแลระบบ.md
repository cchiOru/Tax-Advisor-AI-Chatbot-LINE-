# ออกแบบหลังบ้านสำหรับผู้ดูแลระบบ

เอกสารนี้เป็นการออกแบบ ยังไม่ได้ลงมือทำ
เขียนไว้เพื่อตัดสินใจว่าจะทำหรือไม่ทำ และถ้าทำจะทำแค่ไหน

---

## สรุปข้อเสนอในหนึ่งย่อหน้า

ระบบหลังบ้านที่คุ้มค่าที่สุดสำหรับโครงงานนี้ **ไม่ใช่แดชบอร์ดสวย ๆ ที่โชว์กราฟ**
แต่เป็นหน้าเดียวที่ตอบคำถามว่า **"มีคำถามไหนที่ระบบตอบไม่ดี และต้องเติมความรู้อะไร"**
เพราะนั่นคืองานเดียวที่ผู้ดูแลระบบต้องทำซ้ำ ๆ หลังระบบเปิดใช้งาน
ส่วนที่เหลือเป็นข้อมูลที่ดูปีละครั้งก็พอ ซึ่งเปิดดูจาก pgAdmin ที่มีอยู่แล้วได้

---

## เริ่มจากคำถามว่าใครใช้ และใช้ตอนไหน

ผู้ดูแลระบบของโครงงานนี้คือผู้จัดทำเอง และในอนาคตอาจเป็นเจ้าหน้าที่ที่ดูแลบัญชี LINE ต่อ
งานที่ต้องทำจริงมีอยู่ไม่กี่อย่าง

| งาน | ความถี่ | ทำไม่ได้ตอนนี้เพราะ |
|---|---|---|
| ดูว่ามีคำถามไหนที่ระบบตอบไม่ดี | ทุกสัปดาห์ | ต้องเปิด pgAdmin แล้วเขียน SQL เอง |
| เติมความรู้ใหม่เมื่อกฎหมายเปลี่ยน | ปีละไม่กี่ครั้ง | ต้องเขียนไฟล์ SQL แล้วรันคำสั่ง docker |
| ดูว่ามีคนใช้เยอะแค่ไหน | เดือนละครั้ง | ต้องเขียน SQL เอง |
| ลบข้อมูลผู้ใช้ตามที่ร้องขอ | นาน ๆ ครั้ง | ผู้ใช้ทำเองได้แล้วผ่าน LINE |

**สังเกตว่างานที่ทำบ่อยที่สุดมีอย่างเดียว** คือการดูคำถามที่ตอบไม่ดี
การออกแบบจึงควรทุ่มไปที่งานนั้น ไม่ใช่กระจายไปทำทุกอย่างเท่า ๆ กัน

---

## หน้าที่ควรมี เรียงตามความคุ้มค่า

### หน้าที่ 1 คำถามที่ต้องดู (สำคัญที่สุด)

ไม่ใช่รายการบทสนทนาทั้งหมด เพราะอ่านไม่ไหวและไม่มีประโยชน์
แต่เป็นรายการที่ **คัดมาแล้วว่าน่าจะมีปัญหา** โดยใช้สัญญาณที่ระบบเก็บอยู่แล้ว

| สัญญาณ | ความหมาย | มีข้อมูลแล้วหรือยัง |
|---|---|---|
| `knowledge_hits = 0` | ค้นฐานความรู้ไม่เจออะไรเลย แบบจำลองตอบจากความจำตัวเอง | มีแล้ว |
| `question_category = 'อื่นๆ'` | ระบบจำแนกไม่ออกว่าเป็นคำถามประเภทไหน | มีแล้ว |
| `response_time_ms > 20000` | ตอบช้าจนผู้ใช้เริ่มรู้สึก | มีแล้ว |
| คำตอบมีข้อความแจ้งข้อผิดพลาด | ระบบขัดข้อง | มีแล้ว ค้นจากข้อความได้ |
| ผู้ใช้ถามซ้ำเรื่องเดิมติดกัน | คำตอบแรกไม่ตอบโจทย์ | ต้องเขียนคิวรีเพิ่ม |

**ข้อดีคือไม่ต้องแก้ฐานข้อมูลเลย** ข้อมูลทั้งหมดถูกเก็บอยู่แล้วในตาราง `conversations`
ตั้งแต่ตอนออกแบบระบบเพื่อการวิจัย

สิ่งที่ต้องมีในหน้านี้
- คำถามของผู้ใช้ คำตอบที่ระบบให้ และเหตุผลที่ถูกคัดมา
- ปุ่มเดียวคือ "เรื่องนี้ต้องเติมความรู้" ซึ่งบันทึกไว้เป็นรายการรอทำ
- ไม่ต้องมีปุ่มแก้คำตอบ เพราะระบบไม่ได้ทำงานแบบท่องคำตอบ การแก้ต้องไปแก้ที่ฐานความรู้

### หน้าที่ 2 เติมความรู้ใหม่

หน้าฟอร์มสำหรับเพิ่มรายการเข้าตาราง `tax_law_knowledge` โดยไม่ต้องเขียน SQL

ช่องที่ต้องกรอก ตรงกับโครงสร้างตารางที่มีอยู่
- หมวด
- หัวข้อ
- เนื้อหา
- แหล่งอ้างอิง **ต้องบังคับกรอก** และเตือนถ้าเกิน 200 ตัวอักษร
- ปีภาษี

**ข้อควรระวังที่สำคัญที่สุดของหน้านี้**
ต้องมีปุ่ม "ทดลองค้น" ให้พิมพ์คำถามแล้วดูว่ารายการที่เพิ่งเพิ่มถูกค้นเจอหรือเปล่า
เพราะบทเรียนจากการพัฒนาคือ **การเพิ่มรายการที่ถูกต้องเข้าไป อาจทำให้ระบบตอบแย่ลงได้**
รายการที่ยาวและมีคำสำคัญเยอะจะเบียดรายการที่มีคำตอบจริงตกไปจากงบข้อมูลนำเข้า
เกิดขึ้นจริงมาแล้วกับฐานความรู้ชุดที่ 8

ถ้าไม่มีปุ่มนี้ ผู้ดูแลจะเพิ่มความรู้เข้าไปด้วยความหวังดีแล้วทำให้ระบบแย่ลงโดยไม่รู้ตัว

### หน้าที่ 3 ภาพรวมการใช้งาน

หน้านี้คุ้มค่าน้อยที่สุดในสามหน้า แต่จำเป็นสำหรับการนำเสนอและเขียนรายงาน

- จำนวนผู้ใช้ทั้งหมด แยกตามสถานะความยินยอม
- จำนวนคำถามต่อวัน
- สัดส่วนคำถามแต่ละหมวด
- เวลาตอบเฉลี่ยและช้าที่สุด
- สัดส่วนที่ค้นฐานความรู้ไม่เจอ

**ไม่ควรมี** กราฟที่ดูแล้วไม่นำไปสู่การกระทำอะไร เช่น กราฟเส้นสวย ๆ ที่ดูแล้วก็ผ่านไป

## สิ่งที่ตั้งใจไม่ทำ และเหตุผล

| ไม่ทำ | เหตุผล |
|---|---|
| ระบบล็อกอินหลายผู้ใช้ พร้อมสิทธิ์แยกระดับ | มีผู้ดูแลคนเดียว การทำสิทธิ์ซับซ้อนคือการแก้ปัญหาที่ยังไม่มี |
| หน้าแก้ไขคำตอบรายข้อความ | ระบบไม่ได้ท่องคำตอบ แก้ตรงนี้ไม่มีผลกับคำถามครั้งต่อไป |
| หน้าตั้งค่าคำสั่งระบบผ่านเว็บ | คำสั่งระบบเป็นส่วนที่เปราะที่สุด ควรผ่าน git และชุดทดสอบเสมอ |
| แดชบอร์ดเรียลไทม์ | ไม่มีใครนั่งเฝ้า ข้อมูลย้อนหลังหนึ่งวันเพียงพอ |
| ระบบแจ้งเตือนเข้าอีเมล | ปริมาณการใช้งานยังน้อย เปิดดูเองสัปดาห์ละครั้งพอ |

## ต้องเพิ่มอะไรบ้างในระบบปัจจุบัน

### ฐานข้อมูล

ตาราง `conversations` และ `users` มีข้อมูลครบแล้วสำหรับหน้าที่ 1 และ 3
สิ่งที่ต้องเพิ่มมีตารางเดียว

```sql
-- รายการที่ผู้ดูแลกดว่าต้องเติมความรู้ ไว้ติดตามว่าทำแล้วหรือยัง
CREATE TABLE knowledge_gaps (
    id           SERIAL PRIMARY KEY,
    conversation_id INTEGER REFERENCES conversations(id),
    note         TEXT,
    status       VARCHAR(16) NOT NULL DEFAULT 'open'
                 CHECK (status IN ('open', 'done', 'wontfix')),
    created_at   TIMESTAMPTZ DEFAULT now(),
    resolved_at  TIMESTAMPTZ
);
```

### ส่วนติดต่อผู้ใช้

มีสามทางเลือก เรียงจากงานน้อยไปมาก

| ทางเลือก | งานที่ต้องทำ | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **ใช้ pgAdmin ที่มีอยู่ + ไฟล์คิวรีสำเร็จรูป** | เขียนไฟล์ `.sql` ไม่กี่ไฟล์ | เสร็จในหนึ่งวัน ไม่เพิ่มบริการใหม่ | ต้องคัดลอกคิวรีไปวางเอง ไม่มีปุ่มกด |
| **สร้างเวิร์กโฟลว์ n8n เพิ่มที่รับ HTTP แล้วคืน HTML** | เพิ่มเวิร์กโฟลว์ใหม่ ไม่ต้องเพิ่มบริการ | ใช้ของที่มีอยู่แล้ว ไม่ต้องดูแลเซิร์ฟเวอร์เพิ่ม | n8n ไม่ได้ออกแบบมาทำเว็บ โค้ดจะอ่านยาก |
| **เขียนเว็บแยกต่างหาก** | เพิ่มบริการใน docker compose พร้อมระบบล็อกอิน | ทำอะไรก็ได้ ดูเป็นระบบ | งานเพิ่มมาก และต้องดูแลความปลอดภัยเอง |

**ข้อเสนอคือทำทางเลือกที่หนึ่งก่อน** เขียนไฟล์คิวรีสำเร็จรูปให้ครบ
ใช้จริงสักสองสัปดาห์ แล้วค่อยดูว่าอันไหนที่เปิดดูบ่อยจนควรมีหน้าเว็บ

เหตุผลคือยังไม่มีข้อมูลว่าผู้ดูแลจะดูอะไรบ่อยจริง ๆ
การเดาแล้วสร้างหน้าเว็บทั้งชุดมีโอกาสสูงที่จะสร้างหน้าที่ไม่มีใครเปิด

## คิวรีที่ควรเขียนไว้ก่อน

```sql
-- 1. คำถามที่ค้นฐานความรู้ไม่เจอ เรียงจากล่าสุด
SELECT c.created_at, u.display_name, c.message AS คำถาม
FROM conversations c
JOIN users u ON u.id = c.user_id
WHERE c.role = 'user'
  AND EXISTS (
    SELECT 1 FROM conversations a
    WHERE a.user_id = c.user_id AND a.id = c.id + 1
      AND a.role = 'assistant' AND a.knowledge_hits = 0
  )
ORDER BY c.created_at DESC
LIMIT 50;

-- 2. คำถามที่ระบบจำแนกประเภทไม่ออก
SELECT created_at, message AS คำถาม
FROM conversations
WHERE role = 'user' AND question_category = 'อื่นๆ'
ORDER BY created_at DESC
LIMIT 50;

-- 3. คำตอบที่ช้าเกิน 20 วินาที
SELECT created_at, response_time_ms / 1000.0 AS วินาที, question_category, message
FROM conversations
WHERE role = 'assistant' AND response_time_ms > 20000
ORDER BY response_time_ms DESC
LIMIT 50;

-- 4. คำตอบที่ระบบขัดข้อง
SELECT created_at, message
FROM conversations
WHERE role = 'assistant' AND message LIKE '%ระบบขัดข้อง%'
ORDER BY created_at DESC;

-- 5. ภาพรวมรายวัน
SELECT date(created_at) AS วันที่,
       count(*) FILTER (WHERE role = 'user')      AS จำนวนคำถาม,
       count(DISTINCT user_id)                     AS จำนวนผู้ใช้,
       round(avg(response_time_ms) FILTER (WHERE role = 'assistant')) AS เวลาตอบเฉลี่ย_ms
FROM conversations
GROUP BY 1 ORDER BY 1 DESC;

-- 6. สัดส่วนคำถามแต่ละหมวด
SELECT question_category AS หมวด, count(*) AS จำนวน,
       round(100.0 * count(*) / sum(count(*)) OVER (), 1) AS สัดส่วน
FROM conversations
WHERE role = 'user' AND question_category IS NOT NULL
GROUP BY 1 ORDER BY 2 DESC;

-- 7. สถานะความยินยอมของผู้ใช้
SELECT consent_status AS สถานะ, count(*) AS จำนวน
FROM users GROUP BY 1;
```

## ข้อควรระวังเรื่อง PDPA

หน้าหลังบ้านที่แสดงบทสนทนาของผู้ใช้ **เป็นการประมวลผลข้อมูลส่วนบุคคล**
ต้องสอดคล้องกับสิ่งที่แจ้งไว้ในข้อความขอความยินยอม ซึ่งระบุว่าเก็บไปเพื่อ
จำบทสนทนาก่อนหน้าและปรับปรุงคำตอบให้ดีขึ้น

การเปิดดูเพื่อหาว่าต้องเติมความรู้อะไร **อยู่ในขอบเขตที่แจ้งไว้แล้ว**
แต่ต้องระวังสามข้อ

หนึ่ง หน้าหลังบ้านต้องเข้าถึงได้เฉพาะผู้ดูแล ไม่เปิดสู่อินเทอร์เน็ตโดยไม่มีการยืนยันตัวตน

สอง ถ้าจะแสดงชื่อผู้ใช้ ควรมีเหตุผลรองรับ ในงานหาช่องว่างความรู้ไม่จำเป็นต้องรู้ว่าใครถาม
การซ่อนชื่อไว้เป็นค่าเริ่มต้นจะปลอดภัยกว่าและไม่ทำให้งานยากขึ้นเลย

สาม ข้อมูลของผู้ใช้ที่ไม่ยินยอมจะไม่มีอยู่ในตารางนี้อยู่แล้ว
เพราะระบบไม่บันทึกตั้งแต่ต้น ตรงนี้ไม่ต้องทำอะไรเพิ่ม แต่ควรเขียนไว้ให้ชัด
เพื่อไม่ให้ใครในอนาคตเข้าใจผิดว่าหน้าหลังบ้านเห็นข้อมูลทุกคน

## ข้อเสนอสุดท้าย

ถ้าเวลาเหลือน้อยและต้องเลือกอย่างเดียว **ให้ทำไฟล์คิวรีสำเร็จรูป**
เพราะได้ประโยชน์จริงทันที ใช้เวลาครึ่งวัน และเขียนลงรายงานได้ว่า
ระบบมีเครื่องมือสำหรับผู้ดูแลในการติดตามและปรับปรุงฐานความรู้

หน้าเว็บสวย ๆ ทำให้การนำเสนอดูดีขึ้น แต่ไม่ได้เพิ่มคุณค่าเชิงวิชาการของปริญญานิพนธ์
และมีความเสี่ยงที่จะกินเวลาที่ควรใช้เขียนบทที่ 4 และ 5
