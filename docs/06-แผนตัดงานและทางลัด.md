## ส่วนที่ 1: ตัดได้ พร้อมเหตุผลที่ใช้ตอบกรรมการ

### 1.1 Workflow ตัวที่ 2 (ดึงข้อมูลกฎหมายอัตโนมัติ) — ตัดได้ และควรตัด

**อยู่ในสไลด์ที่ 12** เป็นกล่อง "n8n Workflow Automation insert tax law" ที่ดึงข้อมูลจาก
Open Law Data Thailand API และเว็บไซต์กรมสรรพากร

**ผลการตรวจสอบแหล่งข้อมูลจริง**

| แหล่งข้อมูลที่ระบุในสไลด์ | ข้อเท็จจริงที่ตรวจสอบได้ |
|---|---|
| `api.openlaw.in.th/apis/v2/data` | **ไม่มี API นี้อยู่จริง** โครงการ Open Law Data Thailand เผยแพร่ข้อมูลเป็น**ชุดข้อมูลสำหรับดาวน์โหลด**บน Hugging Face ไม่ใช่บริการ API ที่เรียกแบบสดได้ |
| `rd.go.th/fileadmin/user_upload/tax_calculation/tax_law.json` | ไม่พบไฟล์ กรมสรรพากรไม่ได้เผยแพร่ข้อมูลกฎหมายในรูปแบบไฟล์ JSON สำเร็จรูป |

**สิ่งที่มีอยู่จริงและใช้ได้**

โครงการ Open Law Data Thailand (องค์กรไม่แสวงหากำไร ทำงานร่วมกับสำนักงานพัฒนารัฐบาลดิจิทัล)
เผยแพร่ชุดข้อมูลกฎหมายไทยในรูปแบบที่เครื่องอ่านได้ 2 ชุด

| ชุดข้อมูล | แหล่งที่มา | รูปแบบ | ขนาด |
|---|---|---|---|
| `ocs-krisdika` | สำนักงานคณะกรรมการกฤษฎีกา | JSON Lines แบ่งตามปีและเดือน | 418 MB |
| `soc-ratchakitcha` | ราชกิจจานุเบกษา | JSON Lines | — |

โครงสร้างข้อมูลของ `ocs-krisdika` มีฟิลด์ที่นำมาใช้ได้โดยตรง ได้แก่
`title` (ชื่อกฎหมาย), `sections` (เนื้อหาแยกตามมาตรา), `is_latest` (เป็นฉบับล่าสุดหรือไม่),
`publish_date` และ `reference_url` (ลิงก์ตรวจสอบย้อนกลับไปยังเว็บไซต์ต้นทาง)

สัญญาอนุญาตเป็นแบบ CC-BY 4.0 ใช้งานได้โดยต้องอ้างอิงแหล่งที่มา

**ข้อจำกัดที่ต้องระบุหากนำมาใช้**

ชุดข้อมูลระบุข้อสงวนไว้ชัดเจนว่า *"จัดทำขึ้นเพื่อการศึกษาและพัฒนาเทคโนโลยี
ไม่สามารถใช้อ้างอิงในทางกฎหมายอย่างเป็นทางการได้ กรุณาตรวจสอบกับเอกสารต้นฉบับอีกครั้ง"*
ซึ่งสอดคล้องกับคำเตือนที่ระบบแสดงต่อผู้ใช้อยู่แล้ว

**ข้อสรุปที่แก้ไขแล้ว**

สิ่งที่ต้องตัดคือ **สถาปัตยกรรมแบบเรียก API แบบสด** ตามที่วาดไว้ในสไลด์ที่ 12
เพราะแหล่งข้อมูลไม่ได้ให้บริการในรูปแบบนั้น

แต่**ตัวแหล่งข้อมูลยังใช้ได้** โดยเปลี่ยนวิธีเป็นการนำเข้าข้อมูลแบบครั้งเดียว (bulk import)
ซึ่งเหมาะสมกับลักษณะข้อมูลมากกว่าอยู่แล้ว เพราะกฎหมายภาษีเปลี่ยนแปลงประมาณปีละครั้ง
การเขียนระบบดึงข้อมูลอัตโนมัติแบบต่อเนื่องจึงไม่คุ้มกับความซับซ้อนที่เพิ่มขึ้น

**สิ่งที่ทำอยู่จริงและควรเขียนแทน**

ระบบใช้การนำเข้าข้อมูลด้วยสคริปต์ SQL (`postgres/seed-tax-law.sql`)
ซึ่งผู้ดูแลระบบรันเพื่อปรับปรุงฐานข้อมูลได้ทุกเมื่อ ตรวจสอบย้อนกลับได้
และควบคุมคุณภาพข้อมูลได้ดีกว่าการดึงอัตโนมัติ

**ประโยคที่ใช้เขียนในเล่ม**

> ในระยะแรกผู้วิจัยออกแบบให้มีกระบวนการทำงานอัตโนมัติสำหรับนำเข้าข้อมูลกฎหมาย
> จากบริการข้อมูลเปิดภาครัฐ แต่จากการทดสอบพบว่าแหล่งข้อมูลที่กำหนดไว้ไม่สามารถ
> เรียกใช้งานได้ ประกอบกับข้อมูลอัตราภาษีและค่าลดหย่อนมีการเปลี่ยนแปลงเพียงปีละครั้ง
> ผู้วิจัยจึงปรับมาใช้การนำเข้าข้อมูลด้วยสคริปต์ที่ผู้ดูแลระบบควบคุมได้
> ซึ่งเหมาะสมกับลักษณะข้อมูลมากกว่า และเสนอการเชื่อมต่อบริการข้อมูลเปิดภาครัฐ
> ไว้เป็นแนวทางพัฒนาต่อเมื่อมีบริการที่พร้อมใช้งาน

### 1.2 Embeddings และการค้นแบบเวกเตอร์ — ตัดได้

**อยู่ในสไลด์ที่ 7** ในหัวข้อเครื่องมือที่ใช้ ระบุคำว่า "Data base / Embeddings"

**เหตุผลที่ควรตัด**

ฐานข้อมูลมีเพียง 13 รายการ การใช้ embeddings กับข้อมูลขนาดนี้ให้ประโยชน์น้อยมาก
เมื่อเทียบกับความซับซ้อนที่เพิ่มขึ้น (ต้องติดตั้ง pgvector, เรียก API สร้าง embedding,
จัดการการอัปเดตเวกเตอร์เมื่อข้อมูลเปลี่ยน)

**สิ่งที่ทำแทนและได้ผลจริง**

ระบบใช้การจับคู่คำสำคัญเฉพาะโดเมนพร้อมพจนานุกรมคำพ้องความหมาย
ทดสอบกับคำถามจากฉากสาธิตในสไลด์ทั้งหมด **ค้นเจอ 8 จาก 8 คำถาม**

**สิ่งที่ค้นพบระหว่างทาง ซึ่งควรเขียนในเล่มเพราะเป็นความรู้ที่มีคุณค่า**

ผู้วิจัยทดลองใช้ Full-Text Search ของ PostgreSQL ก่อน แต่พบว่าใช้กับภาษาไทยไม่ได้
ด้วยสองเหตุผล คือ (1) ภาษาไทยเขียนติดกันโดยไม่มีช่องว่างระหว่างคำ ระบบจึงตัดทั้งประโยค
เป็นคำเดียว และ (2) ฟังก์ชัน `plainto_tsquery` ใช้เงื่อนไขว่าทุกคำต้องปรากฏพร้อมกัน
ผลคืออัตราการค้นพบเป็นศูนย์ ซึ่งตรวจพบได้จากข้อมูลที่ระบบบันทึกไว้เอง (`knowledge_hits = 0`)

ข้อค้นพบนี้แสดงให้เห็นความสำคัญของการบันทึกข้อมูลการทำงานของระบบ
เพราะข้อบกพร่องนี้ไม่ปรากฏอาการภายนอก ระบบยังตอบคำถามได้ตามปกติ
เพียงแต่ตอบจากความรู้ในแบบจำลองภาษาแทนที่จะตอบจากฐานข้อมูลที่จัดเตรียมไว้

### 1.3 แบบสอบถามความพึงพอใจ — ตัดแล้วตามที่ตกลง

**สิ่งที่ต้องทำต่อ:** แก้บทที่ 3 หัวข้อ "วิธีการทดสอบและวิเคราะห์ผล"
ให้ตัดหัวข้อการประเมินความพึงพอใจออก มิฉะนั้นเอกสารจะขัดแย้งกับสิ่งที่ทำจริง

หัวข้อที่ต้องแก้คือส่วนที่เขียนว่า "เก็บข้อมูลความพึงพอใจผ่านแบบสอบถามที่ใช้มาตรวัด
แบบลิเคิร์ท 5 ระดับ" และเกณฑ์การแปลความหมายค่าเฉลี่ยทั้งย่อหน้า

**สิ่งที่ใช้ทดแทนได้โดยไม่ต้องทำงานเพิ่ม**

ระบบบันทึกข้อมูลการใช้งานจริงไว้อัตโนมัติแล้ว นำมาใช้แทนได้ทันที

| ข้อมูลที่มีอยู่แล้ว | ใช้อธิบายอะไรได้ |
|---|---|
| `v_response_time_stats` | เวลาตอบสนองเฉลี่ย ส่วนเบี่ยงเบนมาตรฐาน มัธยฐาน เปอร์เซ็นไทล์ที่ 95 |
| `v_retrieval_stats` | อัตราการสืบค้นฐานข้อมูลสำเร็จ |
| `v_daily_usage` | จำนวนผู้ใช้และคำถามรายวัน |
| ตาราง `conversations` | คำถามจริงที่ผู้ใช้ถาม นำมาจัดหมวดหมู่เพื่อวิเคราะห์ความต้องการได้ |

### 3.1 Rich Menu — ไม่ต้องเขียนโค้ดเลย

ใน repository เดิมมีทั้งสคริปต์ Python (`create_rich_menu.py`) และ workflow n8n ตัวที่ 3
สำหรับสร้าง Rich Menu ผ่าน API ซึ่ง**ไม่จำเป็นเลย**

LINE Official Account Manager มีหน้าจอสำหรับสร้าง Rich Menu ให้อยู่แล้ว

1. เข้า https://manager.line.biz/ เลือกบัญชี
2. เมนู **Rich menus** กด **Create**
3. เลือกเทมเพลตแบบ 3 ช่อง
4. อัปโหลดรูป (ขนาด 2500 x 843 พิกเซล หรือ 2500 x 1686)
5. กำหนดให้แต่ละช่องเป็นแบบ **Text** แล้วใส่ข้อความที่จะส่ง

| ช่อง | ข้อความที่ตั้งให้ส่ง |
|---|---|
| ช่องซ้าย | `กำหนดเวลายื่นภาษี` |
| ช่องกลาง | `ขั้นตอนการยื่นภาษี` |
| ช่องขวา | `คำนวณภาษี` |

ข้อความเหล่านี้จะถูกส่งเข้าระบบเหมือนผู้ใช้พิมพ์เอง จึงทำงานกับ workflow ปัจจุบันได้ทันที
โดยไม่ต้องแก้อะไรเลย เพราะ system prompt มีคำสั่งรองรับข้อความทั้งสามนี้อยู่แล้ว

### 3.4 การทดสอบประสิทธิภาพ — ข้อมูลถูกเก็บให้อัตโนมัติแล้ว

บทที่ 3 ระบุว่าต้องทดสอบเวลาตอบสนอง ความสามารถรองรับผู้ใช้หลายคนพร้อมกัน และความเสถียร

ส่วนของเวลาตอบสนองมีข้อมูลจริงครบแล้วในตาราง `conversations`
เรียกดูสถิติได้ทันทีด้วยคำสั่งเดียว

```sql
SELECT * FROM v_response_time_stats;
```

สำหรับการรองรับผู้ใช้หลายคนพร้อมกัน แนะนำให้ปรับขอบเขตเป็นการรายงานว่า
ระบบประมวลผลคำขอแบบเรียงลำดับผ่าน n8n และระบุข้อจำกัดด้านทรัพยากรของเครื่องที่ใช้พัฒนา
แทนการทดสอบภาระงานเต็มรูปแบบ ซึ่งเกินขอบเขตของงานระดับปริญญาตรีที่รันบนเครื่องโน้ตบุ๊ก

## ส่วนที่ 4: สิ่งที่ห้ามตัด

รายการเหล่านี้คือจุดแข็งของงาน หากตัดออกจะเสียน้ำหนักทางวิชาการอย่างมาก

| รายการ | เหตุผล |
|---|---|
