## ลิสต์ที่ต้องทำ เรียงตามลำดับ

### 1. เขียนบทที่ 4 ผลการทดลอง  ← งานหลัก

ตัวเลขพร้อมหมดแล้ว อยู่ในตารางข้างบนและในไฟล์
`evaluation/results/accuracy-gemini-3.1-flash-lite-*.csv` ซึ่งมีคำตอบรายข้อครบ 345 บรรทัด

ประเด็นที่ควรเขียน นอกจากตัวเลข

- **ทำไมได้ 100%** ไม่ใช่เพราะแบบจำลองเก่ง แต่เพราะย้ายงานที่ผิดพลาดง่ายออกจากแบบจำลอง
  การคำนวณอยู่ในโค้ดที่ทดสอบได้ ตัวเลขกฎหมายอยู่ในฐานข้อมูลที่ตรวจสอบได้
  แบบจำลองเหลือหน้าที่แค่เรียบเรียงคำตอบ
- **บั๊กที่วัดผลจับได้ แต่คนอ่านโค้ดไม่เจอ** เช่นกรณีข้อมูลที่ถูกต้องทุกตัวอักษร
  แต่เพิ่มเข้าไปแล้วทำให้ระบบตอบผิด เพราะไปเบียดรายการที่มีคำตอบตกจากงบบริบท
- **ข้อจำกัดของการวัด** คำถาม 115 ข้อเขียนขึ้นเอง ไม่ใช่คำถามจากผู้ใช้จริง
  และแยกความสามารถของรุ่นที่ใช้อยู่ไม่ออกแล้ว

### 2. เขียนบทที่ 5 สรุปและข้อเสนอแนะ

ประเด็นที่มีค่า

- หลักการวางด่านกันด้วยโค้ด ไม่ใช่ด้วยคำสั่งที่เขียนบอกแบบจำลอง
  เพราะคำสั่งบังคับไม่ได้จริง ส่วนโค้ดบังคับได้ทุกครั้ง
- การกันผู้ดูแลอ่านประวัติแชทสองชั้น ทั้งในโค้ดและในสิทธิ์ของฐานข้อมูล
- ปัญหาที่ยังแก้ไม่เสร็จ คือการสะกดคำไทยผิด ซึ่งเป็นข้อเสนอแนะสำหรับผู้ทำต่อ

### 3. แก้เล่มบทที่ 3 ให้ตรงกับระบบจริง

- ตัดแบบสอบถาม Likert ออก เปลี่ยนเป็นปุ่มให้คะแนนสองระดับใน LINE ที่ทำจริงแล้ว
- เปลี่ยน Embeddings เป็นการจับคู่คำสำคัญ พร้อมเหตุผลว่าภาษาไทยไม่มีตัวคั่นคำ
- แก้สเปกฮาร์ดแวร์ให้ตรงกับเครื่องที่ใช้จริง
- เพิ่ม Open Law Data Thailand เป็นแหล่งข้อมูล
- ใส่ตัวเลขโควตาจริงของ Gemini จากหน้า <https://aistudio.google.com/rate-limit>
  แทนการเขียนว่าโควตาจำกัดลอย ๆ

### 4. งานระบบที่ยังเหลือ

- **ไล่ยืนยันช่องต้องคำนวณต่อ** 97 จาก 98 รายการยังเป็นค่าที่ระบบเดาไว้
  เปิดหน้า <http://localhost:8080/knowledge> แล้วเลือกตัวกรองเฉพาะที่ยังไม่มีใครยืนยัน
- **ทำ Rich Menu รายการคำถามที่พบบ่อย** ตอนนี้มีปุ่มตัวอย่างสามปุ่มตอนทักทายแล้ว
  เหลือทำเป็นเมนูถาวรที่กดได้ตลอด
- **แก้ปัญหาการสะกดคำไทยผิด** ที่อาจารย์ทักไว้ เช่น ภาสี พาสี พาศี
  เคยทำต้นแบบได้ 96.4% จากคำผิดที่สร้างขึ้น 2,122 คำ แต่ไฟล์ต้นแบบหายไปแล้ว
  ข้อค้นพบที่ควรจดไว้คือ ระยะห่างที่ยอมรับได้เท่ากับ 1 ให้ผลดีกว่า 2 อย่างมาก (91.6% เทียบกับ 40.6%)
- **วัด Typhoon ใหม่** ด้วยฐานข้อมูลชุดปัจจุบัน เพื่อให้ตารางเปรียบเทียบใช้ฐานเดียวกัน

## ก่อนวัดผลทุกครั้ง ต้องตรวจสามอย่าง

1. **แบบจำลองตรงกันสามที่** `.env` สองบรรทัด และโหนดในเวิร์กโฟลว์
2. **นำเข้าไฟล์ seed และ migration ครบ** โดยเฉพาะชุดที่เพิ่งเพิ่ม
3. **ห้ามใส่ `--fresh` ถ้าต้องการวัดต่อจากของเดิม**
   ระบบตรวจ hash ของการตั้งค่าให้เอง ถ้าการตั้งค่าเปลี่ยนมันจะเริ่มใหม่ให้เองอยู่แล้ว
   การใส่ `--fresh` เองมีประโยชน์เฉพาะตอนที่อยากทิ้งผลเดิมทั้งที่การตั้งค่าไม่ได้เปลี่ยน

```powershell
cd D:\project
node evaluation/run-accuracy-test.js --model=gemini --runs=3
```

**ทุกครั้งที่แก้คำสั่งระบบหรือฐานข้อมูล hash จะเปลี่ยน แปลว่าต้องวัดใหม่**
จึงควรรวบแก้ให้จบก่อนแล้ววัดรอบเดียว ไม่ใช่แก้ทีละนิดแล้ววัดหลายรอบจนโควตาหมด

## ข้อควรระวังที่ห้ามลืม

1. **`.env` ห้าม commit เด็ดขาด** `.gitignore` กันไว้แล้ว แต่ต้องตรวจทุกครั้งก่อน push
2. **ตาราง `revenue_code_sections` ห้ามใช้ตอบผู้ใช้** เป็นฉบับ พ.ศ. 2482 ตัวเลขล้าสมัย
3. **ห้ามนำตัวเลขจาก `revenue_code_current` ไปตอบเรื่องจำนวนเงิน**
   หลายมาตราถูกกฎกระทรวงแก้ภายหลัง เช่น 47(1)(ง) เขียน 10,000 แต่ใช้จริง 100,000
4. **ห้ามให้ระบบสมมติตัวเลขของผู้ใช้** เช่นเงินเดือนหรือจำนวนบุตร
   คำตอบที่เป็นตัวเลขภาษีดูน่าเชื่อถือมาก ผู้ใช้อาจเข้าใจว่าเป็นภาษีของตัวเอง
5. **ผู้ดูแลต้องอ่านประวัติแชทไม่ได้** กันไว้สองชั้นทั้งในโค้ดและในสิทธิ์ฐานข้อมูล
   ถ้าแก้ migration 005 ต้องระวังไม่ให้คืนสิทธิ์โดยไม่ตั้งใจ
