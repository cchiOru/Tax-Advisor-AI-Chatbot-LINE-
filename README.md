# ระบบที่ปรึกษาด้านภาษีด้วยปัญญาประดิษฐ์บนไลน์ โดยใช้ระบบอัตโนมัติ

Development of an AI-Based Tax Advisory System on LINE Using Workflow Automation

ปริญญานิพนธ์ระดับปริญญาตรี ภาควิชาวิทยาการคอมพิวเตอร์และเทคโนโลยีสารสนเทศ
คณะวิทยาศาสตร์ มหาวิทยาลัยนเรศวร

ผู้จัดทำ นายยศกร แจ้งมณี และนางสาวณัฏฐณิชา ป้องป้อม
อาจารย์ที่ปรึกษา ผู้ช่วยศาสตราจารย์ ดร.สัญญา เครือหงษ์

---

## ระบบนี้คืออะไร

เป็นแชตบอตในแอป LINE ที่ตอบคำถามเรื่องภาษีเงินได้บุคคลธรรมดา
พิมพ์ถามเหมือนคุยกับคนทั่วไป แล้วมันตอบกลับมาพร้อมบอกด้วยว่าอ้างอิงกฎหมายมาตราไหน

ตัวอย่างการใช้งานจริง

```
คุณ : เงินเดือน 50,000 บาทต่อเดือน ประกันสังคม 9,000 บาท ต้องเสียภาษีเท่าไหร่

บอท : ภาษีที่ต้องชำระคือ 20,600 บาทค่ะ
      เงินได้ทั้งปี 600,000 บาท
      หักค่าใช้จ่าย 100,000 บาท
      หักลดหย่อนส่วนตัว 60,000 บาท และประกันสังคม 9,000 บาท
      เงินได้สุทธิคงเหลือ 431,000 บาท
      ภาษีที่ต้องชำระ 20,600 บาท

      ข้อมูลนี้เป็นการประมาณการเบื้องต้น กรุณาตรวจสอบกับกรมสรรพากร
      หรือสายด่วน 1161 ก่อนใช้ตัดสินใจจริง
```

ถามได้ทั้งเรื่องคำนวณภาษี ค่าลดหย่อนแต่ละอย่างหักได้เท่าไร ต้องยื่นเมื่อไรใช้แบบไหน
ยื่นช้าแล้วโดนปรับเท่าไร และขอให้ยกถ้อยคำของกฎหมายมาตราที่ต้องการมาดูก็ได้

ที่ต่างจากการถาม ChatGPT คือตัวเลขทุกตัวคำนวณด้วย deterministic code ที่มี unit test กำกับ
ไม่ได้ปล่อยให้ LLM คิดเลขเอง ถามคำถามเดิมสิบครั้งจะได้คำตอบเดิมทุกครั้ง
สถาปัตยกรรมเป็นแบบ RAG คือค้นข้อมูลจริงจาก knowledge base มาก่อน แล้วให้ LLM ตอบจากข้อมูลนั้น

วัดความแม่นยำจากคำถาม 115 ข้อที่อ้างอิงกฎหมายจริง รันสามรอบเป็น 345 ครั้ง ตอบถูกทุกครั้ง
รายละเอียดและข้อควรระวังในการตีความตัวเลขนี้อยู่ในหัวข้อผลการทดลองด้านล่าง
ซึ่งอธิบายไว้ด้วยว่าทำไมคะแนนเต็มร้อยไม่ได้แปลว่าระบบไม่มีข้อบกพร่อง

## ศัพท์ที่ควรรู้ก่อนอ่านต่อ

เอกสารนี้เขียนเป็นภาษาไทยเพราะเป็นปริญญานิพนธ์ภาษาไทย
แต่ทุกคำที่เป็นศัพท์เทคนิคจะมีคำมาตรฐานภาษาอังกฤษกำกับไว้เสมอ
คนที่คุ้นกับงานสายนี้อยู่แล้วอ่านตารางนี้รอบเดียวก็เทียบได้ทั้งเอกสาร

### เครื่องมือและโครงสร้างพื้นฐาน

| คำ | คืออะไร |
|---|---|
| **Docker** | รันซอฟต์แวร์หลายตัวพร้อมกันในคอนเทนเนอร์ (container) โดยไม่ต้องติดตั้งทีละตัว |
| **n8n** | เครื่องมือทำระบบอัตโนมัติแบบลากวาง (workflow automation) รับข้อความจาก LINE ส่งให้ LLM แล้วส่งคำตอบกลับ |
| **PostgreSQL** | ฐานข้อมูลเชิงสัมพันธ์ (relational database) เก็บฐานข้อมูลกฎหมายและบันทึกบทสนทนา |
| **ngrok** | อุโมงค์ (tunnel) ให้บริการภายนอกยิงเข้ามาหาเครื่องที่รันอยู่หลัง NAT ได้ |
| **Webhook** | ปลายทาง HTTP ที่ LINE ยิง POST เข้ามาเมื่อผู้ใช้ส่งข้อความ |
| **API key** | รหัสยืนยันตัวตนกับบริการภายนอก ห้ามคอมมิตขึ้น repository เด็ดขาด |

### ศัพท์ฝั่ง AI ที่ใช้ตลอดทั้งเอกสาร

| คำไทยที่ใช้ในเอกสารนี้ | ศัพท์มาตรฐาน | ความหมายในระบบนี้ |
|---|---|---|
| แบบจำลองภาษา | **LLM** (Large Language Model) | Gemini 3.1 Flash Lite ทำหน้าที่เข้าใจคำถามและเรียบเรียงคำตอบ |
| คำสั่งระบบ | **system prompt** | ข้อความที่กำหนดบทบาทและกฎให้ LLM ทำตาม ส่งไปทุกครั้งที่เรียก |
| ข้อมูลนำเข้า / บริบท | **context** / **prompt** | ทุกอย่างที่ส่งเข้า LLM ในหนึ่งครั้ง รวม system prompt คำถาม และผลการค้น |
| หน้าต่างบริบท | **context window** | ขีดจำกัดจำนวนโทเคน (token) ที่ LLM รับได้ในครั้งเดียว |
| งบบริบท | **context budget** | ขนาดสูงสุดที่เราตั้งเองว่าจะยัดผลการค้นเข้าไปได้เท่าไร ระบบนี้ตั้ง 3,000 ตัวอักษร |
| ฐานข้อมูล | **knowledge base** | ตาราง `tax_law_knowledge` 97 รายการที่ใช้ตอบคำถาม |
| การสืบค้น / ค้นข้อมูล | **retrieval** | ขั้นตอนดึงรายการจากฐานข้อมูลมาแนบเข้า context |
| จับคู่คำสำคัญ | **keyword matching** | วิธี retrieval ที่ใช้ในระบบนี้ แทนที่จะใช้ vector search |
| สถาปัตยกรรมโดยรวม | **RAG** (Retrieval-Augmented Generation) | ค้นข้อมูลจริงมาก่อน แล้วให้ LLM ตอบจากข้อมูลนั้น ไม่ให้ตอบจากความจำล้วน |
| เครื่องมือ | **tool** / **function calling** | ฟังก์ชันที่ LLM เรียกใช้ได้ เช่น เครื่องคำนวณภาษี |
| เรียกเครื่องมือ | **tool call** | เหตุการณ์ที่ LLM ตัดสินใจเรียกฟังก์ชัน แทนที่จะตอบเอง |
| ขั้นตอนกลาง | **intermediate steps** | ผลลัพธ์ที่ tool คืนกลับมา ระบบนี้อ่านค่าจากตรงนี้มาบังคับรูปแบบคำตอบ |
| หน่วยความจำบทสนทนา | **conversation memory** | เก็บบทสนทนาก่อนหน้าไว้ใน PostgreSQL เพื่อให้ถามต่อเนื่องได้ |
| การจำแนกประเภทคำถาม | **intent classification** | ตัดสินว่าคำถามเป็นประเภทไหน ทำด้วยกฎ (rule-based) ไม่ได้ใช้ LLM |
| ตอบมั่วโดยดูน่าเชื่อ | **hallucination** | ความเสี่ยงหลักของงานนี้ แก้ด้วยการบังคับเรียก tool และแนบมาตราอ้างอิง |

### ศัพท์ฝั่งวิศวกรรมและการวัดผล

| คำไทยที่ใช้ในเอกสารนี้ | ศัพท์มาตรฐาน | ความหมายในระบบนี้ |
|---|---|---|
| ชุดทดสอบ | **unit test** / **test suite** | 145 ข้อที่รันได้โดยไม่ต้องเรียก API |
| ด่านตรวจ / บังคับด้วยโค้ด | **guardrail** | กฎที่บังคับในโค้ด ไม่ใช่ขอให้ LLM ทำตาม |
| ตาข่ายรองรับ | **fallback** | ทางสำรองเมื่อทางหลักใช้ไม่ได้ เช่น สลับไป Push API เมื่อ reply token หมดอายุ |
| การถดถอย | **regression** | ของที่เคยทำงานได้แล้วพังเพราะการแก้ครั้งใหม่ |
| ลายนิ้วมือ | **fingerprint** / **cache key** | ค่าแฮชของโค้ดและข้อมูล ใช้ตัดสินว่าผลวัดเดิมยังใช้ได้ไหม |
| โควตา / ถูกจำกัดอัตรา | **quota** / **rate limit** | ข้อจำกัดจำนวนคำขอต่อนาทีและต่อวันของบริการ LLM |
| ลองใหม่แบบถอยเวลา | **exponential backoff** | รอนานขึ้นเรื่อย ๆ ก่อนลองใหม่เมื่อโดน rate limit |
| เวลาตอบสนอง | **latency** | เวลาตั้งแต่ผู้ใช้ส่งข้อความจนได้รับคำตอบ |
| เวลาตอบช้าที่สุด P95 | **p95 latency** | ค่าที่ 95% ของคำขอเร็วกว่านี้ ใช้แทนค่าเฉลี่ยเพราะทนค่าผิดปกติได้ดีกว่า |
| มัธยฐาน | **median** | ค่ากลาง ระบบนี้รายงานคู่กับ p95 เสมอ |
| ตัวชี้วัด | **metric** | ตัวเลขที่ใช้ตัดสินว่าระบบดีขึ้นหรือแย่ลง |
| ความแม่นยำ | **accuracy** | สัดส่วนคำตอบที่ผ่านเกณฑ์ ต่อจำนวนคำถามทั้งหมด |
| สคริปต์ปรับโครงสร้างฐานข้อมูล | **migration** | ไฟล์ SQL ที่แก้โครงสร้างตาราง รันตามลำดับและรันซ้ำได้ |
| ความยินยอม | **consent** | สถานะตาม PDPA ว่าผู้ใช้ยอมให้เก็บข้อมูลหรือไม่ |

## ติดตั้งและใช้งาน

### ถ้าไม่เคยติดตั้งอะไรพวกนี้มาก่อนเลย

อ่าน [docs/01-เริ่มต้นติดตั้งครั้งแรก.md](docs/01-เริ่มต้นติดตั้งครั้งแรก.md) แทน
ไฟล์นั้นอธิบายทุกคลิกตั้งแต่ติดตั้ง Docker สมัคร LINE Official Account ไปจนถึงบอทตอบข้อความได้
เขียนไว้สำหรับคนที่ไม่เคยเขียนโปรแกรมมาก่อน

ส่วนหัวข้อด้านล่างนี้เป็นฉบับย่อ สำหรับคนที่คุ้นกับ Docker และบรรทัดคำสั่งอยู่แล้ว

### สิ่งที่ต้องเตรียม

โปรแกรมที่ต้องติดตั้งในเครื่อง

- Docker Desktop
- Node.js เวอร์ชัน 20 ขึ้นไป ใช้รันชุดทดสอบ
- Python เวอร์ชัน 3.10 ขึ้นไป ใช้สร้างไฟล์เวิร์กโฟลว์และรูปเมนู

บัญชีที่ต้องสมัคร ทั้งหมดสมัครฟรี ไม่ต้องใช้บัตรเครดิต

- บัญชี Google เพื่อขอ API key ของ Gemini ที่ https://aistudio.google.com/apikey
- บัญชี ngrok ที่ https://dashboard.ngrok.com/signup
- LINE Official Account ที่เปิดใช้ Messaging API แล้ว จะได้ Channel access token และ Channel secret

### ขั้นตอนที่ 1 ดาวน์โหลดโปรเจกต์

```bash
git clone https://github.com/cchiOru/Tax-Advisor-AI-Chatbot-LINE-.git
cd Tax-Advisor-AI-Chatbot-LINE-
```

### ขั้นตอนที่ 2 ใส่รหัสของตัวเองลงไฟล์ตั้งค่า

```bash
cp .env.example .env
```

เปิดไฟล์ `.env` ด้วยโปรแกรมแก้ไขข้อความ แล้วแทนที่ค่าที่ยังเป็นตัวอย่างอยู่ 5 บรรทัดนี้

```
POSTGRES_PASSWORD=ตั้งรหัสผ่านฐานข้อมูลเอง
N8N_ENCRYPTION_KEY=ข้อความสุ่ม 32 ตัวอักษร
NGROK_AUTHTOKEN=ค่าที่ได้จาก ngrok
LINE_CHANNEL_ACCESS_TOKEN=ค่าที่ได้จาก LINE Developers
LINE_CHANNEL_SECRET=ค่าที่ได้จาก LINE Developers
GEMINI_API_KEY=ค่าที่ได้จาก Google AI Studio
```

บรรทัดอื่นปล่อยค่าเดิมไว้ได้เลย

ไฟล์ `.env` ไม่ได้อยู่ใน repository นี้เพราะเก็บรหัสลับ และห้ามอัปโหลดขึ้นที่สาธารณะเด็ดขาด

### ขั้นตอนที่ 3 เปิดระบบ

```bash
docker compose up -d
```

รอสักครู่แล้วตรวจว่าขึ้นครบทุกตัว

```bash
docker compose ps
```

ต้องเห็น 4 ตัวคือ `tax-advisor-postgres`, `tax-advisor-n8n`, `tax-advisor-ngrok`, `tax-advisor-pgadmin`
และสถานะต้องเป็น running หรือ healthy ถ้าตัวไหนขึ้น exited ให้ดูสาเหตุด้วย
`docker compose logs ชื่อตัวนั้น`

### ขั้นตอนที่ 4 ใส่ความรู้เรื่องกฎหมายภาษีเข้าฐานข้อมูล

```bash
for f in seed-tax-law seed-tax-law-extra seed-tax-law-full \
         seed-tax-law-cases seed-tax-forms seed-tax-law-deductions-detail \
         seed-tax-law-exempt-and-freelance seed-tax-law-social-security \
         seed-tax-law-modern-income; do
  docker cp postgres/$f.sql tax-advisor-postgres:/tmp/
  docker exec tax-advisor-postgres psql -U n8n_admin -d tax_advisor -f /tmp/$f.sql
done
```

จากนั้นรันสคริปต์ปรับโครงสร้างฐานข้อมูลสำหรับเก็บสถานะความยินยอม

```bash
docker cp postgres/migrations/004-add-consent.sql tax-advisor-postgres:/tmp/m004.sql
docker exec tax-advisor-postgres psql -U n8n_admin -d tax_advisor -f /tmp/m004.sql
```

ตรวจว่า knowledge base เข้าครบ ต้องได้ 97

```bash
docker exec tax-advisor-postgres psql -U n8n_admin -d tax_advisor \
  -c "SELECT count(*) FROM tax_law_knowledge;"
```

จากนั้นดึงตัวบทประมวลรัษฎากรฉบับปัจจุบันจากเว็บไซต์กรมสรรพากร ใช้เวลาราวหนึ่งนาที

```bash
pip install requests beautifulsoup4
python postgres/import-revenue-code-current.py
```

จะได้ไฟล์ `postgres/seed-revenue-code-current.sql` แล้วนำเข้าแบบเดียวกับข้างบน

### ขั้นตอนที่ 5 สร้างและนำเข้าเวิร์กโฟลว์

```bash
python n8n/build-workflow.py
```

จะได้ไฟล์ `n8n/workflows/tax-advisor-workflow.json` จากนั้น

1. เปิดเบราว์เซอร์ไปที่ http://localhost:5678 แล้วสร้างบัญชีผู้ดูแลของ n8n
2. กด Import from File แล้วเลือกไฟล์ที่เพิ่งสร้าง
3. เปิดโหนดที่มีเครื่องหมายเตือนสีแดง แล้วผูก credential ให้ครบ
   มีโหนด PostgreSQL 8 โหนด และโหนด Google Gemini 1 โหนด
4. กดสวิตช์ Active ที่มุมขวาบนให้เป็นสีเขียว

**ทำครั้งเดียวแล้วไม่ต้องผูก credential ซ้ำอีก** หลังผูกเสร็จรอบแรก ให้ไปที่เมนู
Credentials ใน n8n คลิก credential ที่สร้างไว้ แล้วคัดลอกรหัสจากแถบที่อยู่

```
http://localhost:5678/home/credentials/AbCdEf123456
                                       ^^^^^^^^^^^^ นี่คือรหัส
```

นำไปใส่ในไฟล์ `.env` สองบรรทัดนี้

```
N8N_PG_CREDENTIAL_ID=รหัสของ credential ฐานข้อมูล
N8N_LLM_CREDENTIAL_ID=รหัสของ credential LLM
```

ครั้งต่อไปที่รัน `python n8n/build-workflow.py` ไฟล์จะผูก credential มาให้เลย
นำเข้าแล้วกด Active ได้ทันที ไม่ต้องเปิดทีละโหนดอีก

ค่าที่ใช้ผูก credential ของ PostgreSQL

| ช่อง | ใส่อะไร |
|---|---|
| Host | `postgres` |
| Database | `tax_advisor` |
| User | `n8n_admin` |
| Password | ค่าเดียวกับ `POSTGRES_PASSWORD` ในไฟล์ `.env` |
| Port | `5432` |

Host ต้องเป็นคำว่า `postgres` ไม่ใช่ `localhost` เพราะ n8n มองหาฐานข้อมูลจากในเครือข่ายของ Docker

คนจำนวนมากไม่รู้ว่าตัวเองต้องยื่นภาษีหรือไม่ ต้องเสียเท่าไร และลดหย่อนอะไรได้บ้าง

เว็บไซต์กรมสรรพากรมีข้อมูลครบ แต่เขียนด้วยภาษากฎหมาย คนทั่วไปอ่านแล้วตีความเองไม่ได้
สายด่วน 1161 ตอบได้ตรงจุด แต่จำกัดเวลาราชการและต้องรอสาย
สำนักงานบัญชีตอบได้ดีที่สุด แต่มีค่าใช้จ่าย ไม่คุ้มถ้าเป็นคำถามเล็กน้อย
ส่วนแชตบอตปัญญาประดิษฐ์ทั่วไปตอบทันทีและอ่านง่าย แต่ตัวเลขเชื่อไม่ได้ และตรวจสอบที่มาไม่ได้

ข้อสุดท้ายคือสิ่งที่โครงงานนี้ต้องการแก้

### แนวคิดของระบบ

LLM ขนาดใหญ่ตอบคำถามได้ลื่นและอ่านเข้าใจง่าย แต่พอเป็นเรื่องตัวเลขมันคำนวณผิดได้
โดยที่ยังอ้างมาตราถูกต้อง ผู้ใช้จึงไม่มีทางรู้เลยว่าคำตอบผิด

ตัวอย่างที่พบระหว่างพัฒนา เมื่อปล่อยให้ระบบคิดเลขเอง มันอ้างมาตรา 47(1)(ง) ได้ถูก
แต่ลืมหักค่าใช้จ่าย 100,000 บาท และลืมค่าลดหย่อนส่วนตัว 60,000 บาท

โครงงานนี้จึงแยกงานออกเป็นสองส่วน ส่วนที่ต้องถูกต้องแน่นอนเขียนเป็น deterministic code
ที่มี unit test กำกับ ส่วนที่ต้องยืดหยุ่นจึงปล่อยให้ LLM ทำ

| หน้าที่ | ใครทำ | ตรวจสอบอย่างไร |
|---|---|---|
| เข้าใจคำถามภาษาไทยที่ผู้ใช้พิมพ์มา | LLM | ชุดคำถามทดสอบ 115 ข้อ |
| คำนวณภาษี เงินเพิ่ม ค่าปรับ | deterministic code | `test-tax-calculator` 48 ข้อ |
| หาเนื้อหากฎหมายที่เกี่ยวข้อง | retrieval ด้วย keyword matching | `test-retrieval` 6 ข้อ |
| เรียบเรียงให้คนทั่วไปอ่านรู้เรื่อง | LLM | วัดความยาวและรูปแบบคำตอบ |
| บังคับให้มี disclaimer ทุกคำตอบ | guardrail ในโค้ด | `test-reply-guard` 55 ข้อ |
| ไม่เก็บข้อมูลคนที่ไม่ยินยอม | โครงสร้าง workflow | `test-consent-guard` 23 ข้อ |

ชุดทดสอบทั้งหมด 145 ข้อ ทุกข้ออ่านโค้ดและไฟล์เวิร์กโฟลว์ที่ใช้งานจริงมาตรวจโดยตรง
ไม่ได้คัดลอกโค้ดมาทดสอบซ้ำ และไม่ต้องเรียกบริการภายนอกเลย จึงรันได้ทุกครั้งที่แก้ระบบ

ชุดทดสอบ `test-retrieval` มีไว้แยกสาเหตุเวลาระบบตอบผิด ว่าเป็น retrieval failure
คือค้นมาไม่เจอคำตอบ หรือเป็น generation failure คือค้นเจอแล้วแต่ LLM อ่านแล้วตอบไม่ครบ
สองกรณีนี้ต้องแก้คนละที่ retrieval failure แก้ที่ knowledge base หรือวิธีค้น
ส่วน generation failure แก้ที่ system prompt
การวัดผลด้วยการเรียก LLM จริงบอกได้แค่ว่าผิด แต่ไม่บอกว่าผิดที่ขั้นตอนไหน

## ผลการทดลอง

### การสั่งด้วย system prompt อย่างเดียวไม่พอ ต้องบังคับด้วย guardrail ในโค้ด

ตอนแรกใช้วิธีเขียนกฎลงใน system prompt ทั้งหมด ผลออกมาว่า LLM ทำตามบ้างไม่ทำตามบ้าง
เมื่อย้ายกฎเดียวกันไปบังคับด้วยโค้ดในรูปแบบ guardrail ผลดีขึ้นชัดเจน

นี่เป็นข้อค้นพบหลักของโครงงาน สรุปเป็นประโยคเดียวคือ
**สิ่งที่ต้องรับประกันได้ ห้ามฝากไว้กับ prompt ต้องบังคับใน deterministic code เท่านั้น**

| ตัวชี้วัด (metric) | สั่งด้วย system prompt | บังคับด้วย guardrail |
|---|---|---|
| เรียก tool เมื่อโจทย์ต้องใช้ตัวเลข (tool call rate) | 79.5% | 94.9% |
| มีคำเตือนต่อท้ายคำตอบ | ขาดเป็นบางครั้ง | 100% |
| ความยาวคำตอบเฉลี่ย | 729 ตัวอักษร | 404 ตัวอักษร |

ตัวเลขในตารางนี้เป็นการเปรียบเทียบแบบควบคุมตัวแปร วัดสองแบบด้วยชุดคำถามและ knowledge base ชุดเดียวกัน
เปลี่ยนเฉพาะวิธีบังคับ จึงไม่ใช่ตัวเลขล่าสุดของระบบ ผลล่าสุดอยู่ในหัวข้อถัดไป

ระหว่างทดลองยังพบด้วยว่า system prompt ยิ่งยาว LLM ยิ่งทำตามน้อยลง ซึ่งสวนกับที่คาดไว้ตอนแรก

| ความยาว system prompt | จำนวนครั้งที่ไม่เรียก tool |
|---|---|
| 2,275 ตัวอักษร | 2 |
| 3,321 ตัวอักษร | 3 |
| 4,017 ตัวอักษร | 8 |

จึงเขียน system prompt ใหม่ให้สั้นลง และย้ายกฎที่สำคัญที่สุดไปไว้ต้นข้อความ
ซึ่งสอดคล้องกับปรากฏการณ์ที่เรียกว่า lost in the middle คือเนื้อหากลาง prompt ถูกให้น้ำหนักน้อยที่สุด

Typhoon ผ่านสองในสาม โดยติดที่ความเร็ว

หมายเหตุสองข้อที่ต้องอ่านคู่กับตารางนี้

หนึ่ง ผลนี้วัดหลังขยาย knowledge base เป็น 97 รายการ และหลังแก้บั๊ก retrieval

ที่วัดบนฐาน 87 รายการ

สอง สองครั้งที่เกิน 60 วินาทีเป็นคำถามเดียวกัน (Q33) และเป็นคำถามเดิมกับที่พบในการวัดรอบก่อนด้วย
เมื่อเทียบทั้งสามรอบของคำถามนี้พบว่าค่าที่ส่งเข้า tool เหมือนกัน จำนวนครั้งที่เรียก tool เท่ากัน

แปลว่าเวลาที่เพิ่มขึ้นไม่ได้เกิดจากระบบทำงานมากขึ้น แต่เป็นเวลาตอบสนองของบริการภายนอก
สาเหตุที่แน่ชัดยังอธิบายไม่ได้จากข้อมูลที่เก็บได้ จึงบันทึกไว้เป็นข้อสังเกตที่ยังไม่มีคำอธิบาย
ระบบรองรับกรณีนี้ด้วย fallback ไป Push API ตามที่อธิบายในหัวข้อสถาปัตยกรรมข้อ 9

### ข้อควรระวังในการตีความเลข 100 เปอร์เซ็นต์

ตัวเลขนี้แปลว่า **ชุดคำถาม 115 ข้อแยกความสามารถของ Gemini 3.1 Flash Lite ไม่ออกแล้ว**
ไม่ได้แปลว่าระบบไม่มีข้อผิดพลาด และมีหลักฐานยืนยันข้อนี้ชัดเจนจากประวัติการพัฒนา

ชุดคำถามนี้เคยได้ 100% มาแล้วครั้งหนึ่งบนฐานข้อมูล 87 รายการ
เมื่อขยายเป็น 97 รายการแล้ววัดใหม่ คะแนนตกลงมาเหลือ 99.4%
การไล่หาสาเหตุของข้อที่ตกทำให้พบบั๊กจริงสองตัวที่ตอนได้ 100% ซ่อนอยู่โดยไม่มีใครเห็น

บั๊กแรก อยู่ที่ขั้นตอน retrieval วิธีคุม context budget เดิมตัดรายการท้ายสุดออกทีละรายการ
รายการที่มีคำตอบอยู่อันดับสาม แต่รายการอันดับสองยาวผิดปกติจึงเบียดจนอันดับสามถูกตัดทิ้งก่อน
สุดท้ายเหลือแต่อันดับหนึ่งที่ไม่มีคำตอบ แก้โดยเปลี่ยนเป็นไล่ตามอันดับแล้วหยิบเฉพาะรายการที่ใส่ลงในงบได้

บั๊กที่สอง อยู่ที่ intent classification คำถาม "อายุ 65 ปีขึ้นไปได้รับยกเว้นเงินได้เท่าไหร่" ถูกจัดเป็นคำถามคำนวณ
เพราะมีคำว่าเท่าไหร่และมีตัวเลขอยู่ในประโยค ทั้งที่ 65 คืออายุไม่ใช่จำนวนเงิน
ข้อนี้ตอบถูกในการวัดผล แต่ถูกเพราะแบบจำลองรู้คำตอบเอง ไม่ใช่เพราะระบบค้นข้อมูลมาให้
เป็นการผ่านโดยบังเอิญซึ่งอันตรายกว่าการตอบผิด เพราะมองไม่เห็น

เมื่อแก้บั๊กทั้งสองแล้ววัดใหม่ จึงกลับมาได้ 100% อีกครั้ง ซึ่งเป็นเลขที่ปรากฏในตารางข้างต้น

ข้อสรุปเชิงวิธีวิจัย คะแนนเต็มร้อยไม่ได้แปลว่าไม่มีข้อบกพร่อง แต่แปลว่าเครื่องมือวัดมองไม่เห็น
การที่คะแนนลดลงชั่วคราวเมื่อขยายขอบเขตการวัด จึงเป็นสัญญาณว่าเครื่องมือวัดเริ่มทำงาน ไม่ใช่ระบบแย่ลง
ถ้าจะวัดการปรับปรุงต่อจากนี้ ต้องเพิ่มคำถามที่ยากขึ้นหรือทดสอบกับผู้ใช้จริง

| 4 | แยกเกณฑ์ความยาวคำตอบตามประเภทคำถาม | 91.3% | 12.4 วินาที |
| 5–6 | ปรับคำสั่งและลดขนาด context | 91.9% | 15.9 วินาที |

รอบที่ 4 ความแม่นยำตกเพราะย่อคำตอบแรงเกินไปจนตัดข้อมูลที่จำเป็นทิ้ง
จากนั้นการปรับคำสั่งอีกสองรอบได้ผลใกล้เคียงกันหมด คือ 91.3 91.3 และ 91.9 เปอร์เซ็นต์
สิ่งที่เปลี่ยนคือคำถามข้อไหนผิด ไม่ใช่จำนวนข้อที่ผิด
ซึ่งเป็นลักษณะของการชนเพดานความสามารถของแบบจำลอง ไม่ใช่ข้อบกพร่องที่แก้ได้ด้วยการปรับคำสั่ง

ข้อสรุปนี้ยืนยันได้จากคำถามที่ Typhoon ตอบกลับมาเป็นค่าว่างทุกรอบที่วัด
เมื่อเปลี่ยนเป็น Gemini โดยไม่แก้อะไรในระบบเลย คำถามเดียวกันตอบได้ถูกต้องทันที

ไฟล์ผลการวัดอยู่ที่ [`evaluation/results/published/`](evaluation/results/published/)

### ทำไมไม่ใช้ vector search

ทดลองแล้วใช้ไม่ได้ ภาษาไทยเขียนติดกันโดยไม่มีช่องว่างระหว่างคำ (no word delimiter)
PostgreSQL Full-Text Search ทำ tokenization ไม่ได้ วัดจากข้อมูลจริงแล้ว retrieval hit rate เป็นศูนย์
สุดท้ายเปลี่ยนมาใช้ domain-specific keyword matching ที่สร้างขึ้นเอง 332 คู่
วัดแล้วได้ retrieval hit rate 100%

นี่เป็นข้อจำกัดของภาษาไทยที่งานภาษาอังกฤษไม่เจอ และเป็นผลการทดลองที่รายงานไว้ในบทที่ 4

## ฐานข้อมูล

ระบบเก็บข้อมูลกฎหมายไว้สามตาราง แยกหน้าที่กันชัดเจนและห้ามใช้ปนกัน

ข้อควรระวังที่สำคัญที่สุดของระบบคือห้ามนำตัวเลขจาก `revenue_code_current` ไปตอบคำถามเรื่องเงิน
เพราะตัวบทหลายมาตราถูกกฎกระทรวงหรือพระราชกฤษฎีกาแก้ไขค่าในภายหลัง

## ข้อจำกัดของระบบ

ตัวเลขความแม่นยำวัดจากคำถาม 115 ข้อที่ผู้จัดทำสร้างขึ้นเอง
แม้ทุกข้อจะอ้างอิงตัวบทกฎหมายจริงและคำตอบของข้อคำนวณสร้างจากเครื่องคำนวณ
แต่ยังไม่เคยผ่านการทดสอบกับคำถามจากผู้ใช้จริงที่พิมพ์มาเองอย่างอิสระ
ซึ่งมักกำกวมและมีบริบทเฉพาะตัวมากกว่าคำถามที่เตรียมไว้

ข้อจำกัดนี้ไม่ใช่การคาดเดา แต่พิสูจน์แล้วจากการใช้งานจริง
ตอนที่ชุดคำถาม 115 ข้อได้ 100 เปอร์เซ็นต์ การทดลองพิมพ์ถามด้วยมือเพียงไม่กี่คำถาม
กลับพบข้อบกพร่อง 4 จุดที่ชุดคำถามจับไม่ได้เลย ทั้งหมดเกิดจากการถามต่อเนื่องหลายจังหวะ
และการใช้ภาษาแบบที่คนพิมพ์จริง ซึ่งไม่มีอยู่ในชุดคำถามที่เตรียมไว้
ชุดทดสอบจึงถูกขยายจาก 86 เป็น 145 ข้อเพื่อปิดช่องโหว่เหล่านั้น

ระบบครอบคลุมเฉพาะภาษีเงินได้บุคคลธรรมดา ปีภาษี 2567 ยังไม่รองรับภาษีเงินได้นิติบุคคล
และภาษีมูลค่าเพิ่มอย่างเต็มรูปแบบ

ระบบพึ่งบริการภายนอกที่ควบคุมโควตาไม่ได้ ระหว่างวัดผลพบว่าโควตาฟรีของรุ่นที่เป็น preview
หมดตั้งแต่คำถามข้อที่ห้า ทั้งที่เอกสารระบุว่าให้ 1,500 คำขอต่อวัน
การนำไปใช้จริงกับผู้ใช้จำนวนมากจึงต้องประเมินค่าใช้จ่ายส่วนนี้ก่อน

แบบจำลองที่รันในเครื่องยังตอบช้ากว่าเกณฑ์ที่ตั้งไว้ การ์ดจอที่ใช้พัฒนามีหน่วยความจำ 4 GB
ส่วนตัวแบบจำลองใช้ 3.6 GB จึงต้องแบ่งงานบางส่วนไปรันบน CPU
ผลการทดลองปรับค่าต่าง ๆ รวมถึงผลเชิงลบที่พบ บันทึกไว้ใน `n8n/ollama/Modelfile.typhoon-tax`

คำตอบของระบบไม่ใช่คำวินิจฉัยทางกฎหมาย ทุกคำตอบจึงมีคำเตือนให้ตรวจสอบกับกรมสรรพากรติดไว้เสมอ
